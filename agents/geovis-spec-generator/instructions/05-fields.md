## To resolve the spec fields, follow the instructions below:

Variable:
"Scan dataset_catalogue.json (schema.fields[].name/description/unit) and find the field whose description matches the requested concept literally: not a synonym, not a correlate. If none exists ready-made, point to the base field + the operation required (sum/aggregation/join) to derive it. Return: dataset_id, field, grain (spatial.grain.code), whether aggregation is needed and by which key (IBGE code/codarea)."

Expanded prompt — safe proxy:
"Before accepting a variable as the answer: (1) list every catalogue field whose description/tags touch a similar theme (e.g., registry, vulnerability, coverage); (2) for each one, test whether it measures exactly the request or something adjacent (input, cause, correlate), and state the semantic difference explicitly; (3) accept as the direct answer only a field whose description matches the question 1:1; (4) every other related field enters as a 'discarded proxy' with the reason, and is never used without a warning. Goal: never answer question X with data that measures Y just because both sit in the same domain."

mapDataId resolution (mandatory, before building mapData):
"`mapData[].mapDataId` is NEVER invented: it is always, literally, the `id` of a catalogue dataset (one of the `renderableDatasets`) — never a join name, never a source `id`. To choose that `id`: (1) walk ALL catalogue datasets (not only renderableDatasets), comparing `description`/`fields[].description` with the request, following the 'Variable' instruction and the 'Expanded prompt — safe proxy' above; (2) restrict the result to the `renderableDatasets`; (3) if the dataset that matches 1:1 is not in `renderableDatasets`, reply `{"error": "..."}` (there is no acceptable alternative mapDataId). Never generate a `mapDataId` that merely 'looks like' the request — it must be exactly an `id` present in the catalogue."

Combining with municipality/state coverage:
"The geometry of `sources` and the grain of `mapData` must match. Today every dataset in `renderableDatasets` has municipality grain (join by `codarea`/IBGE code against `/geo/geojs-100-mun.json`) — there is no renderable dataset at state grain. If the request asks for the variable aggregated by state, or combined with a state, use `/geo/estados.json` only as an outline/context layer (a layer without `mapDataId` and without its own legend), never as the source of a painted `mapData`. Always paint the variable in the municipality fill. If the request only makes sense at state grain (no per-municipality reading answers it), treat it as an unavailable dataset and reply `{"error": "..."}`. When the request combines two variables (e.g., kitchen points over an IVS choropleth), generate one `mapData` (and one layer with its own `activeLegendId`) per variable — never mix two `mapDataId`s in the same entry."

Spatial coverage (spatial.coverage + spatial.extent):
"Read the chosen dataset's spatial.coverage (exhaustive/partial) and spatial.extent. If partial, list in access.notes/description what falls outside (e.g., no coordinate, only enabled ones) and whether that changes the map reading (real under-representation vs. missing data). Return coverage = extent + coverage caveat. If there is uncertainty or low confidence, choose the smallest granularity the data represents: state(s) or Brazil (BRAZIL_VIEW)."

Time range (temporal.extent + temporal.grain + temporal.frequency + temporal.history):
"Read temporal.status. If described, return extent + grain + frequency + history (snapshot/overwrite). If unknown, state explicitly that there is no date cut — it is a snapshot of the current state — and do not invent a range. If not specified and data exists for the last year, choose it. If not, and the same dataset has more than one temporal version (e.g., \_2025 vs \_all), ask which year the user wants before choosing."
