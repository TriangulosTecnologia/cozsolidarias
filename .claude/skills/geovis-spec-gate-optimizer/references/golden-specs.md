# Golden specs: structural and semantic

The skill uses two golden corpora. They answer different questions and are never merged.

| Corpus | Question it answers | Judged by | Location |
|---|---|---|---|
| Structural | Does the generated spec render the same map as the reviewed spec (geometry, form, sources, layers, legends, totals)? | Code (`gate_pessoas_total.mjs`, `project_spec.mjs compare`) | `GEOVIS_GOLDEN_DIR`, default `tmp/specs/full/verifield`, plus `references/goldens/` for non-spec responses |
| Semantic | Does the spec answer the original question with the right variable, dataset, and unit, and reject the plausible wrong ones? | Rubric (axis b) and human review (Layer C in `evals-architecture.md`) | `references/goldens/semantic/` (schema below; no approved entries yet) |

A structural golden passing does not prove the variable is semantically right. A semantic golden
does not prove the render is identical. Each case may carry one or both.

### Provenance and limits

`tmp/` is in `.gitignore`. The goldens exist in this checkout and are not versioned. Anyone who
clones the repository must copy them to `tmp/specs/full/verifield` or point `GEOVIS_GOLDEN_DIR`
elsewhere. Reproducibility outside this checkout depends on a pending decision: version the goldens
or generate them from a script (see `decisions.md`).

The script that generated `verifield/` is not in the repository. Searching `tmp/`, `scripts/`, and
`.claude/skills/` for `verifield` found no generator. The recorded provenance is "reviewed, copied
from `tmp/`", not "generated by X".

### Validation of the people golden

Reproduced with the gateway algorithm (`src/data-gateway/transformers/toCozinhasPorMunicipio.ts`:
point-in-polygon first, declared code as fallback), over
`src/data-source-static/data/cozinhas_com_geolocalizacao_all.csv` and `public/geo/geojs-100-mun.json`:

- 1,396 CSV rows, 1,388 located by polygon, 8 by declared code, 0 discarded.
- 348 municipalities, sum 789,755, equal to the golden. Per-municipality differences: 0.

The divergences seen earlier (37 values and 7 codes outside the CSV) came from grouping by declared
code without the polygon rule. The golden is correct; the error was in the comparison method.

### People gate

`scripts/gate_pessoas_total.mjs <spec.json>` runs two blocks:

1. Contract invariants: `mapDataId` = `cozinhas_pessoas_atendidas`; no `polygon` layer over that
   dataset; `scaleMaxValue` = maximum of `value`; `sizeBy.thresholds[1]` = maximum.
2. Total oracle: each municipality is recomputed from the CSV with the gateway rule and compared with
   zero tolerance (value by value and in sum).

`--self-test [golden.json]` runs the regression gate. Without a path, it uses
`$GEOVIS_GOLDEN_DIR/_pessoas-atendidas.json`. The golden must pass, and five mutants must fail:
dataset swapped for count, polygon over the total, `scaleMaxValue` doubled, one municipality
missing, and one value shifted by one unit.

Known limit: the oracle reads the static CSV, not the running gateway. If the aggregation rule
changes, the oracle must change with it.

### Clarification response (`references/goldens/coropletico-cozinhas-clarify.json`)

For the count-of-kitchens choropleth request, the route answers HTTP 200 without `spec`, with a
`clarify` (facet `mapType`, default `proportionalCircles`). This is the behavior accepted by decision
D4 (option a). The file stores that captured response from run
`runs/20261027T120609Z--pos-extensao-absoluto-lista`.

### Excluded cases

- Modes with source `vector-tiles` (`cafs.json`): the agent does not emit tiles.
- `assentamentos` modes: the source was removed from `KNOWN_SOURCE_URLS`; the case is a refusal.
- Modes whose value is not reachable by `renderableDatasets`: refusal case, not golden. See
  `R-unreachable-indicator` and `R-derived-rate` in `determinism-map.md`.

### UI corpus (outside the gate)

`scripts/dump_golden_specs.mjs` generates `src/app/(features)/mapas/specs/full-evalued/` from
`buildSpec`. That corpus is coupled to the `/mapas` route, does not feed the gate, and does not
replace the goldens in `GEOVIS_GOLDEN_DIR`. If the directory does not exist, the script must run
before any use.

## Semantic corpus

### Purpose

Structural goldens cannot judge variable choice: a spec can render perfectly and still plot the
wrong metric. The semantic corpus records what a correct answer to a natural-language request must
contain, so selection can be graded against it.

### Entry schema

One JSON file per case in `references/goldens/semantic/<caseId>.json`:

```json
{
  "caseId": "nogolden-pessoas-atendidas-quero-ver",
  "question": "Quero ver o número total de pessoas atendidas pelas cozinhas solidárias por município",
  "intent": {
    "metric": "people served",
    "operation": "sum",
    "unit": "people",
    "geography": "municipality",
    "period": null,
    "filters": []
  },
  "outcome": "spec | clarify | error",
  "errorCode": null,
  "acceptableDatasets": ["cozinhas_pessoas_atendidas"],
  "requiredFields": ["value"],
  "allowedTransformations": [],
  "rejectedAlternatives": [
    { "dataset": "cozinhas_geolocalizadas", "reason": "counts kitchens, not people served" }
  ],
  "review": { "status": "pending-review | approved | rejected", "reviewer": null, "date": null, "justification": null }
}
```

Field rules:

- `outcome` is `spec` when a spec must be produced, `clarify` when the route must ask, `error` when
  it must refuse with `errorCode`.
- `acceptableDatasets` lists every dataset that answers the question. An answer using any other
  dataset fails the semantic check.
- `rejectedAlternatives` lists plausible wrong answers and the reason each is wrong. This is what
  makes the entry a test and not a description.
- `review.status` must be `approved` before the entry counts as a reference. `pending-review`
  entries are graded as not executed, never as passed.
