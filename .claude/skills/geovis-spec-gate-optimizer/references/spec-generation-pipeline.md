# Spec generation pipeline: full-evalued vs runtime-captured

> **Outdated (audit of 2026-10-27).** The evaluation goldens are in `GEOVIS_GOLDEN_DIR` (default `tmp/specs/full/verifield`). `full-evalued/` is only the UI corpus of `dump_golden_specs.mjs`. The commands in sections 3.2 onward that read `full-evalued/` do not run in the current checkout. See `golden-specs.md` and `SKILL.md`.

There are two orthogonal sources of VisualizationSpec in this repository — **golden specs** generated from production (full-evalued) and **test specs** captured at runtime during evaluation (runtime-captured). Each serves a different purpose and follows a distinct flow of generation and validation.

---

## 1. Full-Evalued Specs (Golden Corpus)

**Purpose:** Reference corpus of what the app actually publishes. Ground truth for evaluation.

**Location:** `src/app/(features)/mapas/specs/full-evalued/`

**Content:** 23 JSON files — one per `MapMode` (coropletico, pontos, círculos, assentamentos, etc.) — plus `manifest.json`.

### 1.1 Generation

#### Command:
```bash
node --experimental-strip-types \
  ~/.claude/skills/geovis-spec-gate-optimizer/scripts/dump_golden_specs.mjs [--full]
```

#### Run from:
- The cozsolidarias repo root (`cwd` matters — the gateway resolves data files relatively)

#### Produced by:
- Script: `dump_golden_specs.mjs`
- Function: `buildSpec()` in `src/app/(features)/mapas/geovisSpec.ts`
- Data source: Live data gateway — real data from all datasets

#### Generated artifacts:

| File | Content |
|---------|----------|
| `<mode>.json` | One full spec per MapMode. Schema 2.0, structure identical to what the app renders. |
| `manifest.json` | Provenance metadata (git SHA, geovis version, row counts, timestamp, tested modes). |

### 1.2 Structural characteristics

**What is elided (removed to save size):**
- Raw data in `mapData[].data[]` (14MB+ of row values) — never emitted by the agent anyway
- The agent returns `data: { __placeholder__ }` and `appendRealMapData` injects the real values server-side

**What is kept (and will be scored in eval):**
- Binding structure: `sources`, `layers`, `joins`, `legends`
- Legend scale (`quantitative` vs `categorical`)
- Sample of 3 data rows (enough for scale verification)
- Row count (`legendScale` validation depends on it)

### 1.3 Why it cannot be compared directly with agent output

See `golden-specs.md` § "Why a raw JSON diff does not work" (4 structural divergences):
1. Production specs never use `mapType` — they expand `layers`/`legends` explicitly
2. `mapDataId` in production is generic (`"cozinhas-por-municipio"`); the agent emits real catalogue ids
3. Template invariant present in all 23 (unrequested base layers)
4. Only 14 of the 23 are semantically distinct (the rest are clones with a different payload)

**Always compare against the delta, never against the whole spec.**

### 1.4 Update and versioning

- **Regenerated on every eval round** — not a historical dump, it is always the *current* ideal
- **`manifest.json` says which code generated it** — the immutable provenance. If the git SHA differs, the specs are outdated
- **Never edited by hand** — it is the output of a deterministic function

## 2. Runtime-Captured Specs

**Purpose:** Specs generated by the agent in response to prompts during evaluation. Test basis for validating instruction robustness.

**Location:** `<runs>/<YYYY-MM-DD>T<HH-mm-ss>Z--<variant-slug>/<eval-case-name>/output.json`

**Content:** One JSON spec per eval case, with HTTP status, duration and prompt metadata.

### 2.1 Generation

#### Command:
```bash
scripts/run_eval_case.sh "<prompt>" "<output-file>" [base-url]
```

#### Run from:
- Any directory (uses absolute URLs via `curl`)
- Prerequisite: `pnpm dev` running locally at `http://localhost:3000` (or a custom URL)

#### Produced by:
- Script: `run_eval_case.sh` (wrapper that orchestrates POST + timing)
- Consumer: Managed Agents agent (`ANTHROPIC_AGENT_ID` from `.env.local`)
- Endpoint: `POST /api/ai/spec` (route handler in `src/app/api/ai/spec/route.ts`)

#### Internal flow of one call:

1. **Script builds the JSON body** with `{ prompt }`
2. **POST** → the agent processes (agent system prompt + dynamic `INSTRUCTIONS` + user prompt)
3. **Route handler** validates the JSON, resolves the real `mapDataId`, normalizes scales via `applyCanonicalScales`
4. **Response** returns to the script as `{ httpStatus, durationMs, response }`
5. **Script writes** everything to `<output-file>` and displays the status on stderr

#### Artifacts generated per case:

```json
{
  "prompt": "mapa coroplético do IDHM por município",
  "httpStatus": 200,
  "durationMs": 2847,
  "response": {
    "schemaVersion": 2,
    "mapData": [...],
    "layers": [...],
    "legends": [...],
    ...
  }
}
```

The prompt above is a test input in pt-BR, kept verbatim (choropleth map of IDHM per municipality).

When there is a validation error:
```json
{
  "httpStatus": 422,
  "response": {
    "error": "findMapTypeWithoutMapData: mapType sem mapData"
  }
}
```

### 2.2 Organization structure per variant

Each eval round is versioned in `runs/<runId>/`:

```
runs/2026-09-18T14-03-11Z--poda-legend/
├── versions.json               # required manifest (schema, sources, hashes)
├── evals/
│   ├── evals.json             # case definitions (prompt, golden if applicable, etc.)
│   ├── caso-1/
│   │   └── output.json        # runtime-captured spec
│   ├── caso-2/
│   │   └── output.json
│   └── ...
├── proposed-patch-generic-agent.md
├── proposed-patch-instructions.diff
├── coverage-gate.json
├── benchmark.md
└── benchmark.json
```

### 2.3 Capture flow (step by step)

**Step 1 — Provision the test agent (once per campaign)**
```bash
scripts/provision_test_agent.sh create
# Result: variants/test-agent.json with agentId, version=1
```

**Step 2 — Assemble the eval case dataset**
- File: `evals/evals.json` (skill-creator format)
- Cases: real prompts (personal + production) + cases per R-* rule + reachable golden specs
- Tagging: which case covers which rule (`coverageRuleId`), which is the golden (`golden: "coropletico-idhm.json"`)

**Step 3 — Per tested variant**
1. Update the system prompt of the single agent:
   ```bash
   scripts/provision_test_agent.sh update <slug> <prompt-file> variants/test-agent.json
   ```
2. Run `pnpm dev` with a temporary env var:
   ```bash
   ANTHROPIC_AGENT_ID=<test-agent-id> pnpm dev
   ```
3. For each case in `evals/evals.json`:
   ```bash
   scripts/run_eval_case.sh "$PROMPT" "runs/$RUNID/evals/$CASE_NAME/output.json"
   ```
4. Wait for all cases of the variant before the next `update` (serial, not parallel)

**Step 4 — Scoring and coverage gate**
```bash
node scripts/score_case.mjs <output.json> <golden.json>  # code comparison
node scripts/project_spec.mjs compare <golden-delta> <candidate> # structural axes
```

## 3. Validation Cycle: How the Two Relate

### 3.1 Phase 0 — Immutable setup
```bash
node scripts/dump_golden_specs.mjs
# Generates full-evalued/manifest.json
# → versioning snapshots
```

### 3.2 Phase 1 — Redundancy mapping
- Reads `full-evalued/` (production specs)
- Reads `src/app/api/ai/spec/instructions.ts` + `~/geovis-spec-generator.md`
- Produces `references/determinism-map.md` (rule → validator table)
- Identifies prunable vs essential rules

### 3.3 Phase 2 — Eval design
- Reads `golden-specs.md` to learn the deltas (comparable structure)
- Writes prompts **from the delta**, not from the JSON file
- Delta → prompt example:
  ```
  delta: cozinhas-por-municipio @ /geo/geojs-100-mun.json [polygon] quantitative n=5524
  prompt: "mapa coroplético do percentual de estabelecimentos com CAF por município"
  ```
- Records in `evals/evals.json` with `golden: "coropletico-cafs-percentual.json"` (points to full-evalued)

### 3.4 Phase 3 — Runtime capture
- For each prompt in `evals/evals.json`, runs `run_eval_case.sh`
- Stores the response in `runs/<runId>/evals/<case>/output.json` (runtime-captured)

### 3.5 Phase 4 — Comparison
For cases with a `golden` set:
```bash
node scripts/project_spec.mjs compare \
  src/app/\(features\)/mapas/specs/full-evalued/coropletico-cafs-percentual.json \
  runs/2026-09-18T14-03-11Z--poda-legend/evals/cafs-percentual/output.json
```

Produces:
- `geometry`: 1.0 (correct geometry)
- `form`: 0.8 (close cartographic form)
- `legendScale`: 1.0 (correct quantitative scale)
- `dataset`: `{"verdict": "grader.md"}` (delegated to the semantic agent)

## 5. Decision Flow: When to Use Each

| Question | Source | Why |
|----------|-------|--------|
| "Which spec does the app actually publish in production?" | full-evalued | it is the output of production's `buildSpec()`, never ages (regenerated each campaign) |
| "Can the new instruction still produce the maps that matter?" | runtime-captured + comparison vs full-evalued | measures real robustness, not theoretical |
| "Does the new instruction cover all the rules it promises?" | runtime-captured scores | coverage gate: if 1 R-* case fails, the variant is discarded |
| "Is a prompt rule redundant with validation?" | determinism-map.md | lists which validator already covers it (0 token cost to remove) |
| "How many real eval cases exist?" | full-evalued (14 distinct deltas) vs evals.json | 23 files, 14 unique cases, only 5 reachable by the agent |

## 6. Checklist for Regeneration

If structural changes are needed (new MapMode, new dataset, schema change):

- [ ] Edit `geovisMapMode.ts` if there is a new mode
- [ ] Edit `buildSpec()` if there is new logic
- [ ] Run `dump_golden_specs.mjs` **before** starting the eval
- [ ] Check `manifest.json` — the git SHA must point to the correct commit
- [ ] If `libSchemaVersion` in the manifest > 2: **stop** and resync the agent via `geovis-spec-agent-creator`
- [ ] Update `references/determinism-map.md` if new validators were added
- [ ] Update `references/golden-specs.md` if the interpretation of the delta changed
- [ ] Recreate `evals/evals.json` with cases for the new maps (if applicable)
